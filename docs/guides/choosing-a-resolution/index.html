10m, 50m or 110m? Choosing a world map resolution

Measured on @cublya/world-atlas 3.0.0-beta.2, built from Natural Earth 5.1.2. Published 18 October 2026.

Use 50m for most interactive world maps and every choropleth: it is about 240 KB gzipped and contains all 193 UN member states. Use 110m only for small overview maps where microstates do not matter. Use 10m for maps wider than a few thousand pixels, deep zoom, or print, and load it on demand.

The rest of this guide shows the measurements behind that advice, a way to pick by map width, and two traps: simplifying 10m yourself, and tiny islands in the 10m files.

What 10m, 50m and 110m mean

The names are map scales, not distances. Natural Earth publishes its data at three scales (Natural Earth downloads):

  • 1:10m, 1:10,000,000 (1 cm = 100 km): "The most detailed. Suitable for making zoomed-in maps of countries and regions."
  • 1:50m, 1:50,000,000 (1 cm = 500 km): "Suitable for making zoomed-out maps of countries and regions."
  • 1:110m, 1:110,000,000 (1 cm = 1,100 km): "Suitable for schematic maps of the world on a postcard or as a small locator globe."

Each scale is generalized for its intended size: coastlines are smoothed and features too small to see at that scale are removed. That removal is why the 110m file has fewer countries, not only fewer points.

GeoJSON is what your code actually holds after calling topojson-client's feature: TopoJSON stores each shared border once and delta-encodes integer coordinates (TopoJSON specification, 2.1.3), so the 10m file expands from 3.72 MB to 21.5 MB in memory as JSON text. The SVG row is the total length of the d attributes that d3-geo's geoPath writes for every country on a 960 pixel wide Natural Earth projection. At 10m that is 8.3 million characters of path data for an image with fewer than half a million pixels; most of those points land on top of each other.

Method: Node.js with topojson-client 3 and d3-geo 3.1; sizes from the published files; compression with the system gzip -9 and brotli -q 11; coverage counts IDs from the package's validate script lists. Reproduce with scripts/measure/resolution-metrics.mjs. At 10m, two of the counted states do not draw; see tiny islands at 10m.

Pick by map width

A scale of 1:110,000,000 says how much of the Earth one unit of map covers. Turn it into screen terms: CSS defines 96 pixels per inch (CSS Values and Units, absolute lengths), so one CSS pixel is about 0.26 mm. The equator is 40,075 km long. On a world map where the equator runs across the full width, each resolution reaches its nominal scale at roughly these widths:

ResolutionEquator length on screenEquivalent
110mabout 1,400 pxA full-width page map, unzoomed
50mabout 3,000 pxA 1,000 px map zoomed about 3 times
10mabout 15,000 pxA 1,000 px map zoomed about 15 times

Treat these as a rule of thumb rather than a limit. World projections distort scale away from the equator, and on a high-density screen each CSS pixel has two or three device pixels, so generalization shows earlier than the numbers suggest. Below a resolution's width it simply carries more detail than the screen can show; above it, coastlines start to look angular.

In practice: 110m is right for thumbnails, small locator maps and decorative backgrounds. 50m holds up to full-screen maps on a laptop and a few steps of zoom. Switch to 10m when users zoom past about three times, or when you render for print.

Coverage decides before size does

Natural Earth drops features too small for 1:110m. In the 110m file, that removes 28 UN member states and the Holy See: Andorra, Antigua and Barbuda, Bahrain, Barbados, Cabo Verde, Comoros, Dominica, Grenada, Kiribati, Liechtenstein, the Maldives, Malta, the Marshall Islands, Mauritius, Micronesia, Monaco, Nauru, Palau, Saint Kitts and Nevis, Saint Lucia, Saint Vincent and the Grenadines, Samoa, San Marino, São Tomé and Príncipe, Seychelles, Singapore, Tonga and Tuvalu.

On a choropleth, a missing feature fails silently: the value for Singapore or Bahrain has no shape to colour, and no error tells you. If every country in your data has to appear, start at 50m whatever the map size.

The 10m file adds 14 features over 50m, mostly small territories and disputed or unclaimed areas: Akrotiri, Dhekelia, Gibraltar, the U.S. Naval Base at Guantanamo Bay, Bir Tawil, the Southern Patagonian Ice Field, the Spratly Islands, Scarborough Reef and several reefs and banks. Most have no ISO 3166-1 code, so data keyed by ISO code will not colour them.

Being present is not the same as being visible. At 50m, Monaco is a polygon a fraction of a pixel wide on a 1,000 px world map. If small states matter to your readers, also draw them as point markers or list them next to the map.

Why not simplify 10m yourself?

topojson-simplify can thin a topology to any point budget, so it is tempting to start from 10m and cut it to the size you want. To test it, presimplify the 10m file, then keep the most important 16 % of points, which lands at 84,261 points, close to the 50m file's 80,629 (simplify-coverage.mjs).

Four more UN members collapse to zero area: Monaco, Nauru, the Marshall Islands and Tuvalu. (The Maldives and the Holy See are already degenerate in the unsimplified 10m file; see tiny islands at 10m.) Natural Earth's 50m file, generalized by cartographers rather than by an area threshold, draws all 195 states at a similar point count. Use the published scale closest to your need, and simplify only from there.

Loading strategies

A static import puts the whole file in your JavaScript bundle. That is fine for 110m and usually for 50m: 

import world from "@cublya/world-atlas/countries-50m.json" with { type: "json" };

For 10m, load it only when needed. A dynamic import lets the bundler split it into its own chunk: 

async function loadDetailedWorld() {
  const { default: world } = await import(
    "@cublya/world-atlas/countries-10m.json",
    { with: { type: "json" } }
  );
  return world;
}

Or fetch it from a CDN at runtime. Pin the version so the geometry does not change under you: 

const url = "https://cdn.jsdelivr.net/npm/@cublya/world-atlas@3.0.0-beta.2/countries-10m.json";
const world = await fetch(url).then((response) => response.json());

Whatever you load, convert TopoJSON to GeoJSON once and cache the result. The conversion itself is quick; repeating it on every render is the common mistake.

Tiny islands at 10m

Coordinates in these files are quantized to a grid of 100,000 steps in each direction (source.json records "quantization": 100000), as the TopoJSON specification allows (2.1.2, transforms). Across 360° of longitude that is a step of 0.0036°, about 400 m at the equator; in latitude it is about 190 m.

That is far finer than 50m or 110m detail, but the 10m source contains islands and enclaves smaller than one grid cell. Snapped to the grid, their rings can collapse to zero area or come out wound the wrong way. In 3.0.0-beta.2, the 10m country files contain zero-area rings in the Bahamas, Japan, the Maldives, Mexico, Seychelles, Spain, the U.S. Minor Outlying Islands and the Holy See, and three reversed rings in the Maldives. land-10m.json has 173 zero-area and 7 reversed rings. The 50m files have none (degenerate-rings.mjs).

One consequence for coverage: the Holy See is present in countries-10m.json with its ISO code, so it counts in the coverage table, but its polygon has zero area and draws nothing. At 50m it draws.

d3-geo treats a ring that encloses more than a hemisphere as covering the rest of the sphere. A reversed tiny ring therefore draws as a fill over the whole map. If a 10m map renders as a solid block, this is the likely cause.

Until the files are rebuilt, reverse any ring whose spherical area is larger than a hemisphere after converting to GeoJSON: 

import { geoArea } from "d3-geo";

function fixPolygon(rings) {
  const area = geoArea({ type: "Polygon", coordinates: rings });
  return area > 2 * Math.PI ? rings.map((ring) => [...ring].reverse()) : rings;
}

function fixFeature(feature) {
  const { geometry } = feature;
  if (geometry?.type === "Polygon") {
    return { ...feature, geometry: { ...geometry, coordinates: fixPolygon(geometry.coordinates) } };
  }
  if (geometry?.type === "MultiPolygon") {
    return { ...feature, geometry: { ...geometry, coordinates: geometry.coordinates.map(fixPolygon) } };
  }
  return feature;
}

@cublya/geomap's prepareCountries already does this for every polygon it prepares.

Checklist

  • Every country in your data must appear: 50m or 10m.
  • Small, static overview: 110m, if the missing microstates are acceptable.
  • Zoomable map: 50m first, 10m on demand past about three times zoom.
  • Print or very large exports: 10m, with reversed rings fixed.
  • Pin the package version in CDN URLs.
  • Convert to GeoJSON once and cache it.
